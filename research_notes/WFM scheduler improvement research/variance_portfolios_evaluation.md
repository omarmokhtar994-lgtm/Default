## (a) Why do MIP / CP-SAT solvers show large run-to-run variance?

### Takeaway
Performance variability is a documented structural property of branch-and-bound / CDCL-style tree search. "Neutral" changes (a random seed, row/column order, platform, thread count, tie-breaking) change the search path, and the exponential tree amplifies small differences chaotically. The literature therefore treats performance as a random variable that has to be sampled. It is not a single fixed number. Multi-threaded portfolio solvers such as default CP-SAT add timing nondeterminism on top of this.

### Cited Findings
- **Danna (2008)** first flagged the issue in the MIP community ("Performance variability in mixed integer programming", talk at the MIP 2008 Workshop, Columbia University). Later literature credits Danna [2008] as "the first to highlight the importance of accounting for performance variability when assessing the effectiveness of implementations." — [Danna slides](https://coral.ise.lehigh.edu/mip-2008/talks/danna.pdf); [Ralphs et al., "Assessing the Effectiveness of (Parallel) Branch-and-bound Algorithms"](https://arxiv.org/pdf/2104.10025)
- **Lodi & Tramontani, "Performance Variability in Mixed-Integer Programming", INFORMS TutORials in Operations Research (2013), DOI 10.1287/educ.2013.0112.** MIP solver performance "is subject to some unexpected variability that appears, for example, when changing from one computing platform to another, when permuting rows and/or columns of a model, when adding seemingly neutral changes to the solution process." The tutorial covers the roots of variability, how to recognize it, and "severe misinterpretations" that come from careless benchmark analysis. — [INFORMS](https://pubsonline.informs.org/doi/abs/10.1287/educ.2013.0112); [Semantic Scholar](https://www.semanticscholar.org/paper/Performance-Variability-in-Mixed-Integer-Lodi-Tramontani/3d9750b68283761e8747b3077492ae0e64555c89)
- Concrete cross-platform example cited from this line of work: the same CPLEX 11 release solved one instance in **0 B&B nodes and 2,731 simplex iterations on Linux but 1,426 nodes and 122,948 iterations on AIX.** — [ResearchGate: Lodi & Tramontani](https://www.researchgate.net/publication/281222191_Performance_Variability_in_Mixed-Integer_Programming) (search snippet; also reproduced in [MIPLIB 2010 figure material](https://www.researchgate.net/figure/Example-of-performance-variability-depending-on-the-number-of-threads-Instance-roll3000_fig3_225108563))
- **Koch, Achterberg, et al., "MIPLIB 2010", Mathematical Programming Computation 3 (2011), DOI 10.1007/s12532-011-0025-9.** The paper treats performance as "not deterministic but instead a random variable that can be sampled with computational experiments." It names imperfect tie-breaking as one root cause: most solver decisions (e.g. branching on pseudocost scores) pick the top-scoring candidate, and ties are broken by arbitrary secondary criteria such as index order. Changing variable or constraint order, or the seed, "can drastically impact performance even when the mathematical models are identical." The paper also shows variability as a function of thread count (instance roll3000). — [Springer](https://link.springer.com/article/10.1007/s12532-011-0025-9); [ResearchGate figure](https://www.researchgate.net/figure/Example-of-performance-variability-depending-on-the-number-of-threads-Instance-roll3000_fig3_225108563)
- Even a sequential, in-principle deterministic implementation varies when rows and columns are permuted, because sequence-dependent procedures read the problem in a different order. — [Ralphs et al. 2021 / snippet](https://arxiv.org/pdf/2104.10025)
- Standard MIP benchmarking practice since MIPLIB 2010 is to run each instance under several seeds (commonly **10 random permutations** of the input, generated by SCIP's internal permutation routine) and to summarize dispersion with a variability score (a coefficient-of-variation-type statistic). — [Le Bodic & Nemhauser, "An Abstract Model for Branching..."](https://arxiv.org/pdf/1511.01818) (search snippet)
- **MIPLIB 2017** (Gleixner et al., Mathematical Programming Computation 13 (2021), DOI 10.1007/s12532-020-00194-3): 1,065 instances in the collection and 240 in the benchmark set. Because of performance variability, "one would ideally perform multiple runs using different random seeds or instance permutations." — [Springer](https://link.springer.com/article/10.1007/s12532-020-00194-3); [MIPLIB site](https://miplib.zib.de/)
- **Fischetti & Monaci, "Exploiting Erraticism in Search", Operations Research 62(1):114–122 (2014), DOI 10.1287/opre.2013.1231.** Their hypothesis is that "erraticism is a consequence of the exponential nature of tree search that acts as a chaotic amplifier", so a tiny perturbation of initial conditions leads to very different trees. — [INFORMS](https://pubsonline.informs.org/doi/10.1287/opre.2013.1231); [RePEc](https://ideas.repec.org/a/inm/oropre/v62y2014i1p114-122.html)
- **Fischetti, Lodi, Monaci, Salvagnin & Tramontani, "Improving branch-and-cut performance by random sampling", Math. Prog. Computation 8(1):113–132 (2016).** Identifies one specific source: which of several *alternative optimal LP bases* the root relaxation returns. They propose running the root LP and cut loop several times in parallel with different seeds (a "k-sample" approach) to stabilize and improve performance. The idea shipped in CPLEX 12.5.1 as a parallel root cut loop. — [Springer](https://link.springer.com/article/10.1007/s12532-015-0096-0); [IBM INFORMS 2013 slides "Concurrent Root Cut Loops to Exploit Random Performance Variability"](https://www.slideshare.net/IBMOptimization/2013-11-informsparallelcutloops)
- **Heavy tails (CP/SAT).** Gomes, Selman, Crato & Kautz, "Heavy-Tailed Phenomena in Satisfiability and Constraint Satisfaction Problems", *J. Automated Reasoning* 24:67–100 (2000). Backtrack search runtime distributions "often exhibit large variability", with "very long tails or 'heavy tails'", that are best modelled by distributions that can have infinite mean or variance. Randomization plus rapid restarts "can effectively eliminate heavy-tailed behavior." — [Springer](https://link.springer.com/article/10.1023/A:1006314320276); [dblp](https://dblp.org/rec/journals/jar/GomesSCK00.html)
- **CP-SAT specifics (primary source, `sat_parameters.proto`):**
  - `random_seed`: "At the beginning of each solve, the random number generator used in some part of the solver is reinitialized to this seed."
  - `permute_variable_randomly` / `permute_presolve_constraint_order`: "This is mainly here to test the solver variability." Google's own tests deliberately permute models to measure variability.
  - `interleave_search`: "Experimental. If this is true, then we interleave all our major search strategy and distribute the work amongst num_workers. The search is deterministic (independently of num_workers!)"
  - `interleave_batch_size`: "we schedule and wait for interleave_batch_size task to be completed before synchronizing and scheduling the next batch of tasks."
  - `max_deterministic_time`: "The deterministic time should be correlated with the real time used by the solver."
  - Source: [OR-Tools sat_parameters.proto](https://raw.githubusercontent.com/google/or-tools/stable/ortools/sat/sat_parameters.proto)
- **Why default parallel CP-SAT is nondeterministic.** The maintainers say single-thread search should be deterministic but "default parallel search is not deterministic." Workers share solutions and bounds asynchronously, so thread timing changes what each worker sees. Hitting a *wall-clock* time limit is also inherently nondeterministic ("you might hit it sooner or later"). Determinism also requires building the model identically each time: "the fingerprint in the log should be the same." — [or-tools-discuss: Seeding CP-SAT solver](https://groups.google.com/g/or-tools-discuss/c/lPb1FzhTMt0); [or-tools-discuss: interleave search](https://groups.google.com/g/or-tools-discuss/c/GgU_drn3no4/m/0xuhqJSRBAAJ); [or-tools-discuss: Randomness in CP-SAT search](https://groups.google.com/g/or-tools-discuss/c/nmor0kQc7-8)
- A user reported different optimal solutions between runs of CP-SAT v9.7 with `num_workers=1` and a fixed seed (GitHub issue #3943, Oct 2023, tagged "Modeling/Usage problem", milestone v9.8). Even the "deterministic" single-thread setting can be broken by model-building nondeterminism or by wall-clock limits. — [google/or-tools#3943](https://github.com/google/or-tools/issues/3943)
- A separate report (issue #5400, nurse rostering "NRP Instance23") found a reproducible *first-solution* difference between a model with a 21,058-term objective and the same proto with the objective cleared. The objective is part of what steers the search. — [google/or-tools#5400](https://github.com/google/or-tools/issues/5400)
- **CP-SAT is an internal portfolio.** With **8 workers** (the minimum for the full parallel portfolio) it "blends workers with different linear relaxations (none, default, maximal), core-based search if applicable, a quick_restart subsolver, a feasibility_jump first solution subsolver, and dedicated Large Neighborhood Search subsolvers." **16 workers** adds "a continuous probing subsolver, more first solution subsolvers (random search and feasibility_jump), two dual subsolvers dedicated to improving the lower bound," and more LNS. 24+ workers adds further variants and more LNS. — [OR-Tools docs/troubleshooting.md](https://raw.githubusercontent.com/google/or-tools/stable/ortools/sat/docs/troubleshooting.md); [fossies mirror](https://fossies.org/linux/or-tools/ortools/sat/docs/troubleshooting.md)
- Solving with assumptions "is not compatible with parallelism. Therefore, the number of workers must be set to 1." — [OR-Tools troubleshooting.md](https://raw.githubusercontent.com/google/or-tools/stable/ortools/sat/docs/troubleshooting.md)
- A 2026 study ("When Solvers Get Moody: Quantifying and Predicting Performance Variability in MIP") introduces a *Weighted Variability Score* (WVS). It aggregates dispersion in normalized runtime, final gap, LP iterations and B&B nodes across repeated seeded runs. — [Zenodo record 19478202](https://zenodo.org/records/19478202) (snippet only; I could not read the paper)

### Inferences
- A WFM scheduler whose same-input results differ by 5–34 coverage intervals across seeds is showing the textbook phenomenon, not a bug. With default multi-worker CP-SAT, LNS workers and asynchronous solution sharing are a major source of spread in *final objective at a time limit*. This is anytime (optimization) variability, not only time-to-proof variability.
- The seed alone does not fix a multi-threaded CP-SAT run. A reproducible run needs `num_workers=1`, *or* `interleave_search=true` (deterministic independent of `num_workers`), together with a deterministic time limit (`max_deterministic_time`) in place of `max_time_in_seconds`, and a byte-identical model (same fingerprint).
- Tie-breaking and ordering effects imply that *any* code change that alters model construction order (variable creation order, constraint order, objective term order) acts like a new seed. A single before/after run of a "neutral" refactor can show a large apparent change.

- I could not access the Lodi–Tramontani tutorial full text, the Danna slides, or the MIPLIB 2010 variability tables, so they give no percentages (e.g. "X% of instances vary by more than a factor Y"). The Gurobi Help Center page "What is performance variability?" was blocked.
- I found no published measurement of CP-SAT seed-to-seed objective variance on scheduling or rostering benchmarks. OR-Tools issues and forum threads are anecdotal.
- I could not read the maintainer replies on issue #3943 (GitHub API returned 403), so the root cause there is unconfirmed.
- I found no quantitative published cost (slowdown) of `interleave_search` versus default parallel CP-SAT. The parameter is still labelled "Experimental" in the proto.

## (b) Best-of-N, portfolios, racing, bet-and-run, restarts: value under a fixed wall-clock budget

### Takeaway
Theory and experiments agree. When the runtime or quality distribution is heavy-tailed or high-variance, splitting a budget into several randomized runs (restarts, bet-and-run, parallel portfolios/racing) beats one long run. When a single run's anytime curve is still improving steeply at the end of the budget, splitting the budget sequentially can hurt. On a multi-core machine the "parallel" version (k independent diversified runs at the same wall-clock time, keep the best) is almost free in wall-clock terms and is what modern solvers (CP-SAT portfolio, Gurobi/CPLEX concurrent, SCIP racing, ReXi) do internally.

### Cited Findings
- **Luby, Sinclair & Zuckerman, "Optimal speedup of Las Vegas algorithms", Information Processing Letters 47(4):173–180 (1993).** A universal restart strategy S_univ (the "Luby sequence") achieves expected time O(ℓ_A log ℓ_A), where ℓ_A is the expected time under the *optimal* restart strategy for that algorithm. This is optimal up to a constant factor among universal strategies, so restarting on the Luby schedule costs at most a log factor versus the unknown best cutoff. — [UT Austin PDF](https://www.cs.utexas.edu/~diz/Sub%20Websites/Research/optimal_speedup_of_las_vegas_algorithms.pdf); [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/0020019093900299)
- **Gomes, Selman, Crato & Kautz (JAR 2000).** Heavy-tailed runtime distributions (possibly infinite mean/variance) are the reason restarts help. A "rapid restart strategy eliminates heavy-tailed behavior and takes advantage of short runs, significantly reducing expected solution time." Restarts only help when combined with randomization or learning, so each restart explores a different part of the tree. — [Springer](https://link.springer.com/article/10.1023/A:1006314320276); [overview snippet via search](https://arxiv.org/pdf/1401.4601)
- **Gomes & Selman, "Algorithm portfolios", Artificial Intelligence 126 (2001)** (preceded by "Algorithm Portfolio Design: Theory vs. Practice", UAI 1997). Stochastic algorithms' runtimes vary "significantly from instance to instance and when using different random seeds." A portfolio run in parallel or interleaved on one CPU can have "a dramatic computational advantage". Key insight: *inside a portfolio it can be advantageous to use a more risk-seeking, high-variance strategy* (their MIP example is randomized depth-first search versus traditional best-bound). — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0004370200000813); [UAI 1997](https://mlanthology.org/uai/1997/gomes1997uai-algorithm/)
- **Fischetti & Monaci (Oper. Res. 2014), bet-and-run for MIP.** Make "a number of short sample runs with randomized initial conditions", bet on the "most promising" run chosen by simple criteria, and bring it to completion. The score uses standard MIP information: lower and upper bounds, number of open nodes, lower-bound improvement, and percentage of fractional variables in open nodes. — [INFORMS](https://pubsonline.informs.org/doi/10.1287/opre.2013.1231); [ResearchGate](https://www.researchgate.net/publication/267179036_Exploiting_Erraticism_in_Search)
- **Friedrich, Kötzing & Wagner, "A Generic Bet-and-Run Strategy for Speeding Up Stochastic Local Search", AAAI-17, pp. 801–807 (2017).** Tested on TSP (Chained Lin-Kernighan on TSPlib instances up to 100,000 cities) and Minimum Vertex Cover (FastVC on massive real-world graphs). They compared against single-run, multi-run and Luby-restart strategies. A robust configuration emerged: **40 short runs of 1% of the total budget each (≈40% of budget on exploration), then continue the best run for the remaining ≈60%**, written RESTARTS^{40}_{1%}. It consistently outperformed the single-run baseline. — [ML Anthology](https://mlanthology.org/aaai/2017/friedrich2017aaai-generic/); [arXiv 1609.03993](https://arxiv.org/abs/1609.03993)
- Follow-ups: "An Improved Generic Bet-and-Run Strategy for Speeding Up Stochastic Local Search" (Weise, Wu, Wagner et al., adds performance prediction; arXiv 1806.08984), and "Theoretical results on bet-and-run as an initialisation strategy" (Lissovoi, Sudholt, Wagner, Zarges, GECCO 2017). — [arXiv 1806.08984](https://arxiv.org/pdf/1806.08984); [ACM DL GECCO'17](https://dl.acm.org/doi/10.1145/3071178.3071329)
- **Carvajal, Ahmed, Nemhauser, Furman, Goel & Shao, "Using diversification, communication and parallelism to solve mixed-integer linear programs", Operations Research Letters 42(2):186–189 (2014), DOI 10.1016/j.orl.2013.12.012.** Runs multiple diversified B&B trees in parallel that share incumbents and bound information, with benefits shown on MIPLIB 2010. This is cited, together with UG's "racing ramp-up", as a static parallelization scheme. — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0167637714000236)
- **"Race, Exchange, Improve: Finding high-quality MIP solutions quickly" (arXiv 2609.05954, Sept 2026; SCIP built-in plus the external "ReXi").** "MIP solvers are known for their performance variability, and a diversified portfolio can transform this behavior into an asset." Workers exchange primal solutions, primal bounds and variable bounds, and LP-free heuristics get a dedicated thread. Result: **ReXi with 10 threads reached a primal integral of 0.0107, versus 0.0568 for single-thread SCIP and 0.0178 for SCIP concurrent mode.** It is reported as the fastest non-commercial solver on the MIPFEAS benchmark. — [arXiv html](https://arxiv.org/html/2609.05954) (snippet; recent preprint, not peer-reviewed)
- The Fischetti et al. (2016) "k-sample" parallel root cut loop is a form of racing: exploit variability at the root, then keep the best root state. — [Springer](https://link.springer.com/article/10.1007/s12532-015-0096-0)
- CP-SAT's default multi-worker mode *is* a portfolio with sharing: different LP relaxation levels, core search, quick_restart, feasibility jump, LNS workers. — [OR-Tools troubleshooting.md](https://raw.githubusercontent.com/google/or-tools/stable/ortools/sat/docs/troubleshooting.md)
- CP scheduling practice: job-shop CP approaches combine weighted-degree heuristics, geometric restarts (cutoff s, sr, sr², …) and nogood learning from restarts. — [Grimes & Hebrard, JSP with setup times and time-lags (CPAIOR 2010)](https://link.springer.com/chapter/10.1007/978-3-642-13520-0_19); [Solution-Guided Multi-Point Constructive Search for JSP (Beck, JAIR 2007)](https://arxiv.org/pdf/1110.2743)

### Inferences
- **When is k×(T/k) better than 1×T (sequential split on one machine)?** Let q(t) be a single run's objective at time t and σ(t) the seed-to-seed spread. Best-of-k of length T/k wins roughly when E[max of k draws at T/k] > E[q(T)], i.e. when σ(T/k)·c_k > q(T) − q(T/k). Here c_k is the expected maximum of k standard normals, which I computed as c_2≈0.56, c_3≈0.85, c_4≈1.03, c_8≈1.42, c_16≈1.77. Splitting helps when (i) the anytime curve has plateaued, so the tail of a long run adds little, and (ii) spread across seeds is large. It hurts when a single run still improves steadily near T. If the distribution is heavy-tailed or bimodal ("lucky vs. stuck" runs), max-of-k gains are larger than the normal approximation suggests. Friedrich et al.'s 40×1% + continue-best design gets the best of both: diversity early, depth late.
- **Parallel (not sequential) best-of-k is the cheap win.** If the production machine has spare cores, k independent CP-SAT runs with different seeds (each with fewer workers), keeping the best, costs no extra wall-clock time. Caveat: CP-SAT's own workers already form a diversified sharing portfolio. The trade-off is "one 16-worker run with sharing" versus "two 8-worker runs without sharing". This has to be measured per workload. Below 8 workers the full CP-SAT portfolio is not activated, so running many 1–4-worker instances may lose portfolio diversity.
- **Worked example for the stated scheduler.** Same-input runs vary by 5–34 coverage intervals. If that is the range over ~10 seeds, where the expected range ≈3.08σ (computed), then σ ≈ 1.6–11 intervals. Best-of-4 (same wall-clock time, 4 processes) is then expected to gain ≈1.03σ ≈ 2–11 intervals over a typical single run. Best-of-8 gains ≈1.42σ ≈ 2–16 intervals. This matters on a ~100–250 interval scale, and it is often larger than the gain from a typical heuristic tweak. It also removes the bad tail: the worst of k runs is never returned.
- **Bet-and-run adaptation for CP-SAT.** Launch k seeded runs for a short phase, e.g. 5–10% of the budget. Kill all but the best by incumbent objective (or objective plus bound gap), then continue the survivor, warm-started with the incumbent via solution hints, for the remaining budget. The Friedrich/Fischetti evidence makes this worth testing, but the specific split has to be tuned on the scheduler's own instances.

## (c) How to run statistically sound A/B evaluations of solver/heuristic changes under this noise

### Takeaway
Treat each (instance, seed) run as a sample from a distribution. Use many seeds × many instances, pair by instance, and use nonparametric paired tests (Wilcoxon signed-rank for two variants; Friedman plus post-hoc tests or F-race for several). Size the experiment with a power calculation (Campelo & Takahashi). Fix the time budget in *wall-clock* terms on dedicated hardware, or use deterministic time for reproducibility. Guard against over-tuning with a held-out instance set and a pre-declared primary metric. MIPLIB-style practice (≥3–10 permutation seeds per instance, shifted geometric means) is the floor, not the ceiling.

### Cited Findings
- **Campelo & Takahashi, "Sample size estimation for power and accuracy in the experimental comparison of algorithms", Journal of Heuristics 25(2):305–338 (2019).** A method to compute *both* the number of problem instances (for a target statistical power at a given standardized effect size over a problem class) *and* the number of runs per instance (so the per-instance difference estimate hits a target standard error). Implemented in the R package **CAISEr**, which uses closed formulas for the number of instances given desired power and standardized effect size. It was later generalized to more than two algorithms (J. Heuristics 2020, doi 10.1007/s10732-020-09454-w). — [arXiv 1808.02997](https://arxiv.org/abs/1808.02997); [Springer](https://link.springer.com/article/10.1007/s10732-018-9396-7); [CAISEr manual](https://cran.r-project.org/web/packages/CAISEr/refman/CAISEr.html); [multi-algorithm extension](https://link.springer.com/article/10.1007/s10732-020-09454-w)
- **Demšar, "Statistical Comparisons of Classifiers over Multiple Data Sets", JMLR 7:1–30 (2006).** Recommends "the Wilcoxon signed ranks test for comparison of two classifiers and the Friedman test with the corresponding post-hoc tests for comparisons of more classifiers over multiple data sets." The Wilcoxon test is the nonparametric alternative to the paired t-test: it ranks per-dataset differences by magnitude and compares positive against negative rank sums. (This is the standard reference imported into optimization benchmarking.) — [JMLR PDF](https://www.jmlr.org/papers/volume7/demsar06a/demsar06a.pdf)
- **Birattari, Stützle, Paquete & Varrentrapp, "A racing algorithm for configuring metaheuristics", GECCO 2002, pp. 11–18 (F-Race).** Runs all surviving configurations on instances sampled one by one. After each step a nonparametric **Friedman test** checks for differences, and inferior configurations are dropped via pairwise tests "as soon as enough statistical evidence is gathered against them". This is a sequential-testing design that stops early on clear losers. Iterated F-Race / irace generalizes it. — [Semantic Scholar](https://www.semanticscholar.org/paper/A-Racing-Algorithm-for-Configuring-Metaheuristics-Birattari-St%C3%BCtzle/64247308dd5d534d37174feb6315043b233e49a8); [Birattari et al., "F-Race and Iterated F-Race: An Overview"](https://link.springer.com/chapter/10.1007/978-3-642-02538-9_13)
- **Eggensperger, Lindauer & Hutter, "Pitfalls and Best Practices in Algorithm Configuration", JAIR 64:861–893 (2019).** Practical applications of algorithm configuration "are prone to several (often subtle) pitfalls in the experimental design that can render the procedure ineffective." The paper catalogues them (e.g. how time is measured, over-tuning to training instances) and proposes best practices. Domains named include SAT, AI planning and scheduling. — [JAIR](https://jair.org/index.php/jair/article/view/11420); [arXiv 1705.06058](https://arxiv.org/abs/1705.06058)
- **MIPLIB-style benchmarking convention:** per-instance runs under multiple permutation seeds (10 in several studies; a 2026 practitioner benchmark spec uses 3 permutation seeds, 300 s, 60 instances, shifted geometric means). Seeds are a "performance-variability control (not a tuning knob)." — [Le Bodic & Nemhauser snippet](https://arxiv.org/pdf/1511.01818); [example benchmark issue](https://github.com/thegoodengineers/SANKHYA/issues/504) (practitioner, low authority)
- **Time-fair protocol (arXiv 2509.08986, 2025).** Proposes that each algorithm get an identical wall-clock budget per instance, with restarts and internal adaptivity allowed, instead of equal function evaluations, which hide per-iteration overhead. Recommends anytime performance curves, expected running time (ERT) and time-based performance profiles, plus a reproducibility checklist. — [arXiv 2509.08986](https://arxiv.org/abs/2509.08986) (preprint)
- Lodi & Tramontani warn that not analysing benchmark results carefully can produce "severe misinterpretations": a change that "helps" may only be reshuffling the search path. — [INFORMS TutORials](https://pubsonline.informs.org/doi/abs/10.1287/educ.2013.0112)
- CP-SAT reproducibility tools: `num_workers=1` (deterministic single thread), `interleave_search` + `interleave_batch_size` (deterministic regardless of worker count), `max_deterministic_time` (limit that does not depend on machine load), and a stable model fingerprint. Wall-clock limits are inherently nondeterministic. — [sat_parameters.proto](https://raw.githubusercontent.com/google/or-tools/stable/ortools/sat/sat_parameters.proto); [or-tools-discuss](https://groups.google.com/g/or-tools-discuss/c/lPb1FzhTMt0)

### Inferences (recommended evaluation protocol for the WFM scheduler)
1. **Unit of analysis.** For each instance i, run variant A and variant B on the *same* set of seeds s = 1..m under the same budget and hardware, then compute the per-instance mean (or median) over seeds, d_i = mean_B,i − mean_A,i. Pairing by instance removes between-instance difficulty variance, which is usually the largest variance component. Pairing by seed does *not* remove seed noise: because of the butterfly effect, seed s under A and seed s under B follow uncorrelated search paths, so seeds should be treated as independent replicates, not matched pairs.
2. **How many seeds and instances.** Per-instance seed noise σ ≈ 1.6–11 intervals (inferred above). The standard error of a per-instance difference with m seeds per arm is σ√(2/m): m=10 gives ≈0.63σ (≈1–7 intervals), m=20 gives ≈0.45σ, m=30 gives ≈0.37σ. To detect a mean improvement δ with paired-by-instance testing at α=0.05 and 80% power, the number of instances is n ≈ ((1.96+0.84)·σ_d/δ)² ≈ 7.8·(σ_d/δ)². Here σ_d is the SD of the d_i across instances, which includes both seed noise and real instance-to-instance effect heterogeneity. Example: σ_d = 6 intervals and δ = 3 intervals gives n ≈ 32 instances. Use CAISEr (Campelo & Takahashi) to optimize the instances × runs split formally. A practical default is **≥20–30 representative instances × ≥10 seeds per variant**, and more seeds for the noisier instances (CAISEr allocates runs adaptively to meet a target standard error).
3. **Test and report.** Primary test is a Wilcoxon signed-rank test on the d_i. Report the effect size as the median d_i with a bootstrap 95% CI (resample instances; within each instance, resample seeds), the win/tie/loss count across instances, and, for runtime metrics, shifted geometric means. Also report dispersion changes (per-instance SD, worst-of-m), because a change can improve the mean while widening the tail, and production sees single runs.
4. **Sequential testing / early stopping.** Use racing (F-Race style: Friedman/Wilcoxon after each instance batch, drop clear losers), or a pre-specified group-sequential or alpha-spending plan. Do not "peek until p<0.05", which inflates false positives.
5. **Avoid forking paths / over-tuning.** Pre-register the primary metric (e.g. coverage shortfall in intervals at a fixed 60 s budget), the instance set, seeds, budget and test *before* running. Keep a held-out instance set for final confirmation (Eggensperger et al.). Count every variant tried, and correct (Holm) when several are compared.
6. **Reproducible vs. production-realistic runs.** For *debugging and regression* (did this change alter behaviour?), use deterministic mode (`num_workers=1` or `interleave_search=true`, `max_deterministic_time`, fixed seed, stable model build order), so any difference is caused by the change. For *performance A/B*, test under the production configuration (multi-worker, wall-clock limit) with many seeds on dedicated or pinned hardware, and don't run jobs concurrently in ways that steal cores. Deterministic mode measures a different solver configuration than production.
7. **Production recommendation for the 5–34-interval spread.** (i) Adopt parallel best-of-k seeds (k = 2–4, sized to available cores, keeping ≥8 CP-SAT workers per run where possible so the internal portfolio stays active), or a bet-and-run variant (short diversified phase, then continue the best from its incumbent via hints). (ii) Evaluate every heuristic change against that *best-of-k* production pipeline, not against single lucky or unlucky runs. (iii) Treat any claimed improvement smaller than about the per-instance seed SD (≈2–11 intervals) as unproven unless it survives the paired multi-instance test above.
